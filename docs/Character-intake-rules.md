# Character intake and lore provenance rules

Version 1 • 15 November 2026 • applies to Memories research and the evidence handed to JetSetCraft.

## Intake checklist

1. Preserve the user's chosen display name and aliases, but give every character a stable ID and distinguish similarly named characters. Mark unresolved identities explicitly.
2. Add an official/source entry first. Find creator-authored biographies, lore posts, project pages and original publications before relying on fan summaries.
3. Store each claim with its source URL, author/rights holder, source type, continuity/version, access state and check date. Distinguish a live primary-page read from an indexed excerpt or user-supplied lead.
4. Tag sources as creator-authored, official publisher, licensed adaptation, fan reference or unresolved. A fan wiki can help discovery but cannot silently become author canon.
5. Record publication, upload, reupload, game release, revision and fictional-event dates separately. Never replace a missing original date with an update timestamp. Preserve year/month-only precision.
6. Keep official continuities, editions, rewrites and user-created adaptations separate. Conflicting claims stay visible with their scopes and evidence; do not select a convenient answer without support.
7. Creator website/social/support links must be self-linked or independently corroborated by a primary source. Record redirect destination and unreadable destinations where relevant. Never guess a handle, Patreon URL or membership tier.
8. Mark spoiler-bearing lore. Summarize briefly and link; do not copy full creator articles, private messages, paid lore or entire books.
9. Review public-safe scope before publication. Do not publish private correspondence, access tokens, paid attachments or the user's uploaded art merely because related character metadata is public.
10. Review rights per asset and component: character concept, text, model, rig, texture, image, voice and music can have different owners/terms. A credit, bookmark, purchase or support payment does not itself grant reuse.
11. Preserve access failures. No bypass of login, age, bot or explicit approval blocks; no alternate publication route for held content.
12. Record completeness honestly: which sections/pages were reviewed, pagination remaining, inaccessible sources, dates unknown and next evidence needed.

## Cross-project states

Keep these states independent:

| Dimension | Example states |
|---|---|
| Memories identity | user lead → primary corroborated → unresolved conflict |
| Lore research | scoped sources → incomplete inventory → reviewed within stated scope |
| Asset rights | unknown → permission evidence collected → allowed only within recorded conditions |
| JetSetCraft | requested → design specification → implementation → tests → native acceptance |
| Publication | local draft → approved write → remote verified → deployed verified |

A Memories favorite does not mean an asset is cleared or implemented in JetSetCraft. A successful repository write does not prove a deployed UI or native-game test. User-requested female/femboy variants are project adaptations, not statements about source canon.

JetSetCraft handoffs must include stable character ID, source/author list, continuity, intended adaptation, exact permission conditions, attribution wording, unknowns and current project state. Retain existing source records rather than overwriting them with newer interpretations.
